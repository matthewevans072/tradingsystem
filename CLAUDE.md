# Signal Desk — notes for future development sessions

Read START-HERE.md for the user-facing view. This file covers what you must preserve when changing the code.

## Never break these
- **The user's data is sacred.** `data/signal-desk.sqlite` holds real holdings, entry prices and reports. Never reseed, migrate destructively or overwrite it with example data. Schema changes go in `server/db.js` `MIGRATIONS` as new, additive entries; never edit an applied migration.
- **No trading.** Do not add brokerage order or trading-permission integrations.
- **No silent estimates.** Missing or stale quotes stay missing/stale with a label, and the last valid value is kept. The real workspace never falls back to demo data. Never reconstruct session high/low from scheduled checks.
- **Currencies:** USD and CAD totals are computed separately; combine only with a stored, dated FX rate (`fx_rates`).
- **Instrument identity:** an instrument is `(symbol, exchange)` with a currency. Unconfirmed instruments (`identity_status != 'confirmed'`) are not priced. Ambiguous tickers (catalog `ambiguity`, and SPCX always) get no description until confirmed.
- **Secrets** live only in `.env`, read by `server/config.js`. Everything logged or returned in errors passes through `redact()`. Never send keys to the browser.
- **Local only by default:** `server/index.js` refuses non-loopback binding unless remote access is explicitly enabled with a token. Keep the Host-header, Origin and `X-Signal-Desk` CSRF checks.
- **Untrusted content:** news text is rendered via text nodes (`public/lib/ui.js` `h()`), never `innerHTML`, and passed to the AI analyst fenced in `<untrusted_item>` with a JSON-schema response.
- **Assessments** (`server/assessments.js`) must not derive actions from entry price, must not add on a fall alone or sell on a rise alone, must require confirmed cash for CONDITIONAL_ADD and a complete risk profile for sizing. Action labels come only from rules; the AI analyst only explains.
- **Ask Signal Desk (server/agent/)**: tools are read-only. The only write path is `propose_record_change` → `chat_proposals` (pending) → user Confirm → existing audited functions. `checkUserIntent` requires the quoted request to appear in the user's latest message with the instruction verb leading its clause, refuses questions, hypothetical framings ("simulate:", "scenario:", "same but … instead"), orders to trade anywhere in the message, future plans, other people's trades and anything inside quoted or attributed text, and requires the change's key values (ticker, quantity, price, amount, type, currency, direction, thesis…) to match that message. `checkAccountAndCurrency` matches account names in the request's sentence only (longest match, canonical name) and asks which currency when the account holds both. `positionChange` previews a trade by replaying the ledger with the row as `extra` in `deriveLedger` (never writing to the database), so backdated entries are valued at their date and refused if they break a later entry. `confirmProposal` rebuilds the change and refuses if its `stateKey` (the records it depends on) changed, and is tied to the conversation id. All arithmetic shown to the user comes from `calc.js`/portfolio code, never the model; scenario cash is per account and currency. Unknown fees are never treated as $0: net figures stay null and before-fee fields are returned instead. Every returned record is registered in the turn's `Ledger` (refs R1…) so answers cite sources, including status refs for unavailable data; third-party text is wrapped with `untrusted()` and the user's own notes with `owner_note` (still data, not instructions). The guard and intent check are regression-tested against labelled corpora (`tests/fixtures/guard-corpus.json`, `intent-corpus.json`, run by `tests/guard.test.js`); add a labelled case for every miss or false positive you fix, don't tune a rule without re-running the whole corpus, and measure on sentences you have not tuned on before trusting a change (the guard scored about 80% recall / 95% specificity on fresh held-out text; corpus score is not generalisation). The guard does not know today's date, so a claim dated today reads as the owner's own recorded trade. `validateAnswer` runs `guardText` from `guard.js` over every answer field (claims that a trade was placed, executed, filled or is in progress, or that a record was changed, judged per sentence by structure — any past/perfect/progressive/emphatic verb with the assistant, the app or no subject acting on the owner's things, passives on owner-scoped nouns, and state claims like "your USD cash is now 0" — not by verb lists; exemptions such as negation, hypotheticals, dates and reported speech count only when they govern the claim's own clause; the loop asks the model once to rephrase before removing them), drops follow-ups that would pass the intent check, relabels `external_fact` points that cite only media reports or archived briefings as `reported_claim`, and adds a `data_gap` note for cited stale market data. Prior turns are sent as plain text only, so each answer re-fetches data.
- **Agent loop (`agent.js`)**: `submit_answer` must arrive alone (otherwise it gets an error result and the loop continues; in the last round the bundled calls run first, their refs are not citable, and the answer carries a note, or an issue if a bundled proposal failed); an answer with no tools run is marked partial whenever it states figures or portfolio facts; follow-up chips are checked sentence by sentence against `ACTION_START` and `checkUserIntent`; the automatic stale-data note is suppressed only by a model data_gap that cites the stale ref or names the instrument (ticker or company name) with a staleness word; a text-only reply gets one nudge; large tool results are shortened by `fitResult` (valid JSON, note of what was cut); `budgetCheck` runs before every model call; one turn per conversation at a time (`ctx.chatBusy`); the HTTP layer aborts the turn when the client disconnects. Responses are streamed; content before a server-side `fallback` boundary is dropped (`usableContent`). Spend is priced per model from `usage.iterations` and kept in `data/chat-usage.json`, shared by both workspaces; an unpriced model is refused while a cap is set. Each call reserves an estimate (`reserveSpend`) that `budgetCheck` counts until the call is recorded; a dropped or aborted stream is charged an output estimate from the streamed characters (max_tokens once a thinking block started) so the cap errs high; an unreadable spend file pauses chat (fail closed) and is re-read on every check so deleting it takes effect without a restart. Request options a model rejects (`fallbacks`, `output_config.effort`, strict tools) are turned off one per retry, up to three retries in one call.
- **Tool schemas**: only the tools in `STRICT_TOOLS` are sent with `strict: true`, because the API limits strict schemas per request (20 strict tools, 24 optional and 16 union-typed parameters); `tests/agent.test.js` checks this with `strictSchemaStats`. Strict tools list every property as required (nullable where optional); other tools validate input in their handlers. When adding a tool: register ledger refs for everything it returns (status refs when data is missing), wrap untrusted text, and add it to the no-write test in `tests/agent.test.js`.
- **Ledger maths (`portfolio.js`)**: `deriveLedger(db, { asOf, extra })` replays splits at the start of their effective date; daily P/L converts start-of-session shares to post-split units on a split's effective date, a position's dailyPct uses the same denominator as the totals (start value plus same-session buys), and a position not held during its quote's session has null daily P/L (never the quote's change_pct). `sessionMixNote` flags totals that span sessions.
- **Earnings and FX**: `refreshEarnings` passes listings (symbol, exchange, provider symbol) to providers and records non-US listings a provider cannot check as not covered, never as "checked, no date"; events link to the matched listing. `boc.js` stores every observation of the recent-rates response, and the FX effect in `dailyAttribution` is shown only when the session's rate and the previous Bank of Canada business day's rate are both stored.
- **Scheduler**: slots are unique (`briefings.slot_key`); late beyond the grace window means `missed`, never sent late.

## Layout
- `server/` — `index.js` (HTTP + security), `api.js` (routes), `db.js` (schema/migrations/audit), `portfolio.js` (ledger → positions, average cost, splits, FX decomposition), `importer.js` (CSV preview/apply/dedupe), `calendar.js` (NYSE/TSX rules, verified 2026–27), `freshness.js`, `marketdata.js` + `providers/` (Twelve Data, Finnhub, SEC, Bank of Canada, demo), `news.js`, `analytics.js`, `assessments.js`, `briefings.js`, `scheduler.js`, `alerts.js`, `delivery.js` (SMTP/ntfy), `analyst.js` (Claude), `backup.js`, `catalog.js` + `catalog/securities.json`.
- `public/` — no-build SPA: `app.js` (router/API), `views/*.js`, `lib/ui.js`, `lib/charts.js`, `styles.css`.
- `tests/` — `node --test`; provider tests use fixtures because the dev sandbox has no network. Agent tests (`agent.test.js`, `agent-safety.test.js`, fixtures in `agent-helpers.js`) use a scripted backend.
- `scripts/agent-eval.js` — seeds a test portfolio and lets an evaluator play the model against the real tools without an API key (used for prompt/tool evaluation).

## Catalog
`server/catalog/securities.json` holds the plain-English descriptions (official source URL, review date, verification status). Entries were checked against official-source search excerpts on 2026-10-21; re-verify periodically. User edits are stored in the `descriptions` table and take precedence.
