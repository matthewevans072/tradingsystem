# Signal Desk — notes for future development sessions

Read START-HERE.md for the user-facing view. This file covers what you must preserve when changing the code.

## Never break these
- **The user's data is sacred.** `data/signal-desk.sqlite` holds real holdings, entry prices and reports. Never reseed, migrate destructively or overwrite it with example data. Schema changes go in `server/db.js` `MIGRATIONS` as new, additive entries; never edit an applied migration.
- **No trading.** Do not add brokerage order or trading-permission integrations.
- **No silent estimates.** Missing or stale quotes stay missing/stale with a label, and the last valid value is kept. The real workspace never falls back to demo data. Never reconstruct session high/low from scheduled checks.
- **Currencies:** USD and CAD totals are computed separately; combine only with a stored, dated FX rate (`fx_rates`).
- **Instrument identity:** an instrument is `(symbol, exchange)` with a currency. Unconfirmed instruments (`identity_status != 'confirmed'`) are not priced. Ambiguous tickers (catalog `ambiguity`, and SPCX always) get no description until confirmed.
- **Secrets** live only in `.env`, read by `server/config.js`. Everything logged or returned in errors passes through `redact()`. Never send keys to the browser.
- **Local only by default:** `server/index.js` refuses non-loopback binding unless remote access is explicitly enabled with a token. Keep the Host-header, Origin and `X-Signal-Desk` CSRF checks.
- **Untrusted content:** news text is rendered via text nodes (`public/lib/ui.js` `h()`), never `innerHTML`, and passed to the AI analyst fenced in `<untrusted_item>` with a JSON-schema response.
- **Assessments** (`server/assessments.js`) must not derive actions from entry price, must not add on a fall alone or sell on a rise alone, must require confirmed cash for CONDITIONAL_ADD and a complete risk profile for sizing. Action labels come only from rules; the AI analyst only explains.
- **Ask Signal Desk (server/agent/)**: tools are read-only. The only write path is `propose_record_change` → `chat_proposals` (pending) → user Confirm → existing audited functions. `checkUserIntent` requires the quoted request to appear in the user's latest message with an instruction in the quote or in another clause of the user's own words that points back to it, refuses questions, hypothetical framings ("simulate:", "scenario:", "same but … instead"), orders to trade anywhere in the message, future plans, other people's trades and anything inside quoted or attributed text, and requires the change's key values (ticker, quantity, price, amount, type, currency, direction, thesis…) to match that message. `checkAccountAndCurrency` takes the account from the request's sentence (longest match, canonical name), else the one account named anywhere in the message, and asks which currency when the account holds both. `trade_date` must be stated (or today, yesterday, a weekday, N days ago); omitted means today. `positionChange` previews a trade by replaying the ledger with the row as `extra` in `deriveLedger` (never writing to the database), so backdated entries are valued at their date and refused if they break a later entry. `confirmProposal` rebuilds the change and refuses if its `stateKey` (the records it depends on) changed, and is tied to the conversation id. All arithmetic shown to the user comes from `calc.js`/portfolio code, never the model; scenario cash is per account and currency. Unknown fees are never treated as $0: net figures stay null and before-fee fields are returned instead. Every returned record is registered in the turn's `Ledger` (refs R1…) so answers cite sources, including status refs for unavailable data; third-party text is wrapped with `untrusted()` and the user's own notes with `owner_note` (still data, not instructions). The guard and intent check are regression-tested against labelled corpora (`tests/fixtures/guard-corpus.json`, `intent-corpus.json`, run by `tests/guard.test.js`); add a labelled case for every miss or false positive you fix, don't tune a rule without re-running the whole corpus, and measure on sentences you have not tuned on before trusting a change (measured on fresh blind text it had not been tuned on: about 63–64% recall of claims and 93–97% specificity; corpus score is not generalisation). Simulation markers (simulated, paper, backtest, forward test, Strategy Lab, hypothetical account) exempt a trade statement only within its own clause or noun phrase. The guard does not know today's date, so a claim dated today reads as the owner's own recorded trade. `validateAnswer` runs `guardText` from `guard.js` over every answer field (claims that a trade was placed, executed, filled or is in progress, or that a record was changed, judged per sentence by structure — any past/perfect/progressive/emphatic verb with the assistant, the app or no subject acting on the owner's things, passives on owner-scoped nouns, and state claims like "your USD cash is now 0" — not by verb lists; exemptions such as negation, hypotheticals, dates and reported speech count only when they govern the claim's own clause; the loop asks the model once to rephrase before removing them), drops follow-ups that would pass the intent check, relabels `external_fact` points that cite only media reports or archived briefings as `reported_claim`, and adds a `data_gap` note for cited stale market data. Prior turns are sent as plain text only, so each answer re-fetches data. Trade statuses: every ledger item for a trade or order carries `tradeStatus`, set by the tool that read the record: PROPOSED (`propose_record_change`; the proposal's status is its sub-state), SIMULATED (`simulate_trade(s)`; Strategy Lab items of kind simulation) or USER-REPORTED (each transaction row, with origin manual, csv, screenshot or chat_proposal). BROKER-CONFIRMED is reserved and `Ledger.add` refuses it. `validateAnswer` (`tradeClaims` in agent.js) removes trade statements whose stated status no cited record backs (for the short answer, the records are all of this turn's) and always removes broker-confirmed wording; details get `tradeStatuses` from their cited refs only. Regression tests: `tests/agent-trade-status.test.js`. The detector is rule-based and has known misses; re-run the guard corpus before tuning it.
- **Agent loop (`agent.js`)**: `submit_answer` must arrive alone (otherwise it gets an error result and the loop continues; in the last round the bundled calls run first, their refs are not citable, and the answer carries a note, or an issue if a bundled proposal failed); an answer with no tools run is marked partial whenever it states figures or portfolio facts; follow-up chips are checked sentence by sentence against `ACTION_START` and `checkUserIntent`; the automatic stale-data note is suppressed only by a model data_gap that cites the stale ref or names the instrument (ticker or company name) together with a staleness word or quote/price/market data; a text-only reply gets one nudge; large tool results are shortened by `fitResult` (valid JSON, note of what was cut); `budgetCheck` runs before every model call; one turn per conversation at a time (`ctx.chatBusy`); the HTTP layer aborts the turn when the client disconnects. Responses are streamed; content before a server-side `fallback` boundary is dropped (`usableContent`). Spend is priced per model from `usage.iterations` and kept in `data/chat-usage.json`, shared by both workspaces; an unpriced model is refused while a cap is set. Each call reserves an estimate (`reserveSpend`) that `budgetCheck` counts until the call is recorded; a dropped or aborted stream is charged an output estimate from the streamed characters (max_tokens once a thinking block started) so the cap errs high; an unreadable spend file pauses chat (fail closed) and is re-read on every check so deleting it takes effect without a restart. Request options a model rejects (`fallbacks`, `output_config.effort`, strict tools) are turned off one per retry, up to three retries in one call.
- **Tool schemas**: only the tools in `STRICT_TOOLS` are sent with `strict: true`, because the API limits strict schemas per request (20 strict tools, 24 optional and 16 union-typed parameters); `tests/agent.test.js` checks this with `strictSchemaStats`. Strict tools list every property as required (nullable where optional); other tools validate input in their handlers. When adding a tool: register ledger refs for everything it returns (status refs when data is missing), wrap untrusted text, and add it to the no-write test in `tests/agent.test.js`.
- **Ledger maths (`portfolio.js`)**: `deriveLedger(db, { asOf, extra })` replays splits at the start of their effective date; daily P/L converts start-of-session shares to post-split units on a split's effective date, a position's dailyPct uses the same denominator as the totals (start value plus same-session buys), and a position not held during its quote's session has null daily P/L (never the quote's change_pct). `sessionMixNote` flags totals that span sessions.
- **Earnings and FX**: `refreshEarnings` passes listings (symbol, exchange, provider symbol) to providers and records non-US listings a provider cannot check as not covered, never as "checked, no date"; events link to the matched listing. `boc.js` stores every observation of the recent-rates response, and the FX effect in `dailyAttribution` is shown only when the session's rate and the previous Bank of Canada business day's rate are both stored.
- **Strategy Lab (`server/strategy/`, `strategy/`)**: a simulation only. Its databases are `data/strategy-lab.sqlite` / `strategy-lab-demo.sqlite` (`store.js` refuses the portfolio files); it never reads real cash or holdings, never creates proposals and has no order path. The rules are pre-registered (`strategy/RULES.md`, `ENGINE-SPEC.md`, `VALIDATION-PLAN.md`, `universe-v1.json`, `splits-v2.json` (splits-v1's dates plus `excludedSessions`, removed for every symbol by `dropExcludedSessions` wherever run bars are loaded and not expected by the readiness checklist; `splits-v1.json` kept unchanged), `acceptance-v1.json`): never edit a released config or the criteria in place — a rule change is a new version in `strategy/configs/` with an entry in `PARAMETER-LOG.md` saying which data had been seen. The engine is deterministic and must stay free of look-ahead (`tests/strategy-engine.test.js` checks prefix invariance, snapshot round-trips and determinism). The holdout runs once per version/config/mode (`lab_holdout_runs`); a repeat needs a reason and is marked contaminated. Demo Lab data is synthetic and labelled; the real Lab never shows synthetic data. Synthetic results are never performance evidence. The TradingView receiver (`webhook.js`) is off unless configured, listens on loopback only, and only journals. Chat tools for the Lab are read-only and must not call the Lab's job methods. Market data: `lab_bars` rows carry `adjustment` and `feed`, and `lab_bar_sets` logs every stored download or import (store.js migration 2); within the history window a symbol's bars must never mix sources, feeds or adjustments (`storeBarSet` throws `MixedSourceError` unless the owner replaces them), and a run uses only symbols the readiness checklist (`readiness.js`, `GET /api/lab/readiness`, `strategy/DATA-READINESS.md`) marks READY — never shorten a split or swap an instrument silently. History sources: `sources/alpaca.js` (SIP, split-adjusted; keys `ALPACA_API_KEY_ID`/`ALPACA_API_SECRET_KEY` in `.env` only) and Twelve Data (intraday unadjusted). Forward-test results are reported separately (`GET /api/lab/forward-report`) with missed, late and expired signals.
- **HXR (`server/hxr/`, `strategy/hxr/`, `public/views/hxr.js`)**: a simulation only, real workspace only, in its own database `data/hxr-sim.sqlite`. `openHxrDb` resolves links and refuses the portfolio, demo and `strategy-lab*` files, and any file with non-`hxr_` tables. It never reads real holdings or cash, never touches the Strategy Lab or its holdout ledger, has no order or paper-trading path, and never imports `delivery.js` or `alerts.js` (`tests/hxr-service.test.js` checks this statically). The only host is `https://data.alpaca.markets`, and redirects are refused so keys cannot leak. The rules, candidates, periods and criteria are pre-registered. The active set is `hxr-prereg-3a` (`service.js` `PREREG_FILES` and `preregManifest`): `PREREGISTRATION.md` + `-2.md` + `-3.md` + `-3a.md`, `ENGINE-SPEC.md`, `universe-hxr-v3.json` (basket A of ten with `techAi` tags), `periods-hxr-v3.json` (development, validation, final used once, fullList), `criteria-hxr-v3a.json` (G6 = 9 of 10; V1–V2; `selection.pickRule`; benchmarks `hold` and `hold_day_one`), `configs/hxr-hold-0.1.0.json` and the nine `hxr-x1a…x3c-0.3.0.json`. Only the six X1/X2 candidates can be picked; X3A–C are the owner's comparison; C1–C3 (prereg-1) and X1–X3 (prereg-2) are superseded and never run. Never edit any of them in place; a change is a new version logged in `strategy/hxr/EXPERIMENT-LOG.md`. The development pick (`runSelection`, ledger kind `selection`), the validation run (`runValidation`, kind `validation`) and the final run (`runEvaluation`, kind `evaluation`) each run once (`hxr_ledger`, append-only); a repeat needs a reason and is marked contaminated and can never PASS or validate. The development pick is refused while `selection.pickRule` is `pending_owner_choice` (amendment 3b recorded `ending_value` on 2026-10-23); only the single winner is frozen (`hxr-1.0.0`) and validated; the final run refuses to start unless `settings.validation.outcome` is `validated`; no runner-up is ever run. The pick's ten neighbouring settings are reported only: if that phase fails the pick stays stored and `runNeighbours` (`POST /api/hxr/selection/neighbours`) runs them later with no ledger row. Every pass/fail test (G2–G6, V2, the pick) is judged against both benchmarks, and the day-one hold is derived from the candidate by `holdDayOneConfig` (hold rule, `benchmark.baseHash`), never a file. The engine (`engine.js`, `hxr-engine-3`) decides after the close on completed daily bars and fills at the next open, with whole shares, no negative cash, dividends and splits. `account.allocation = risk_sized` configs use pooled cash: positions sized at the decision close from the planned loss and the position, open-risk, tech/AI and cash caps (alphabetical order; a cap that does not apply is `null`), an initial-loss level `L0 = entry − multiple × typical move` on every exit rule, the account-decline pause (buys lapse, exits run; a lapsed or cancelled buy-back keeps the buy-back rule, only a never-held or lapsed initial/fresh entry enters at any price), splits applied to `L0` and to sized pending buys, rule state updated for every sleeve before the equity point and sizing, and the fresh-entry policies after a missed rebound (`stay_out`, `fresh_entry_recovery_point`, `fresh_entry_after_sessions`, counted from the sale); `equal_sleeves` configs behave as before. Its prefix-invariance, future-change, snapshot and determinism tests (`tests/hxr-rules-2.test.js`, `hxr-rules-3.test.js`) must keep passing. `buildInputs` passes each symbol's `techAi` tag to backtests; the data hash covers market data and listings only, not tags; every stored run records `details.codeRevision` (`service.js` `CODE_REVISION`; bump it with any change that alters results) and `details.symbolsHash` (runs without `codeRevision` ran with the tags dropped, EXPERIMENT-LOG entries 17-18). Costs use only spread samples dated on or before the fill. SPCX is never downloaded or priced until the owner confirms it, and bars before each symbol's `listedFrom` are never used (NBIS before 2024-10-21 is Yandex). The prospective account stamps `recorded_at` just before writing, and `on_time` means recorded before the next open; news is untrusted text, first-seen timestamps only, never sent to a model, and in this version never changes a decision. PASS means eligible for the owner's review only, and historical price-only results are never described as evidence for a news-informed HXR.
- **Range-trend (`server/rangetrend/`, `strategy/range-trend/`)**: a simulation only, separate from HXR and the Strategy Lab, with its own results database `data/range-trend-sim.sqlite` (`store.js` `openRtDb` refuses the portfolio, demo, `strategy-lab*` and `hxr*` files and any file with non-`rt_` tables; `rt_ledger` is append-only). Market data is read at run time only, read-only, through HXR's data layer from `data/hxr-sim.sqlite`. The rules are `PLAN-DRAFT.md` (sections 3, 4, 6a); the owner's decisions and build approval are in its section 0 and `EXPERIMENT-LOG.md` entry 1. Only the eight configs in `config.js` `PLANNED_CONFIGS` can run, each once; the one reserve re-runs a run invalidated by a verified defect (defect, verification and correction required; the broken result kept). `runPractice` refuses to start unless `EVALUATION-PROTOCOL.md` contains a filled-in `**Pick rule:**` line; the evaluation and the prospective journal have no code path and need a separate instruction. Levels for decision day t use closes up to t−1 only; prefix-invariance, future-change, determinism and snapshot tests (`tests/rangetrend-engine.test.js`) must keep passing. Every run stores `codeRevision` (`config.js` `CODE_REVISION`; bump it with any change that alters results) and `symbolsHash`. No threshold of Tier 2 or 3 is enforced and no winner is selected automatically. Never a broker, order or paper-trading API path.
- **Scheduler**: slots are unique (`briefings.slot_key`); late beyond the grace window means `missed`, never sent late.

## Layout
- `server/` — `index.js` (HTTP + security), `api.js` (routes), `db.js` (schema/migrations/audit), `portfolio.js` (ledger → positions, average cost, splits, FX decomposition), `importer.js` (CSV preview/apply/dedupe), `calendar.js` (NYSE/TSX rules, verified 2026–27), `freshness.js`, `marketdata.js` + `providers/` (Twelve Data, Finnhub, SEC, Bank of Canada, demo), `news.js`, `analytics.js`, `assessments.js`, `briefings.js`, `scheduler.js`, `alerts.js`, `delivery.js` (SMTP/ntfy), `analyst.js` (Claude), `backup.js`, `catalog.js` + `catalog/securities.json`.
- `public/` — no-build SPA: `app.js` (router/API), `views/*.js`, `lib/ui.js`, `lib/charts.js`, `styles.css`.
- `tests/` — `node --test`; provider tests use fixtures because the dev sandbox has no network. Agent tests (`agent.test.js`, `agent-safety.test.js`, fixtures in `agent-helpers.js`) use a scripted backend.
- `server/strategy/` + `strategy/` — Strategy Lab engine, validation, Lab service/API/forward test, Pine version, rules and research docs; `scripts/strategy-backtest.js` (reproducible runs), `strategy-compare-tv.js`, `strategy-pine-parity.mjs` (optional PineTS check).
- `server/hxr/` + `strategy/hxr/` — HXR hold/exit/re-enter simulation: `config.js`, `store.js`, `source.js` (Alpaca market data only), `data.js` (inputs, spread table, readiness), `engine.js`, `metrics.js` (report items, G1–G6, V1–V2, both benchmarks, the pick rules), `service.js` (download, runs, ledgers, prospective account), `api.js` (`/api/hxr/*`); page `public/views/hxr.js`; tests `tests/hxr-*.test.js`.
- `server/rangetrend/` + `strategy/range-trend/` — range-trend simulation: `levels.js` (range/trend definitions), `engine.js` (sizing, fills, exits), `metrics.js` (benchmarks, Tier 2 descriptions), `store.js`, `config.js`, `service.js` (practice runs, gated); tests `tests/rangetrend-*.test.js`.
- `scripts/agent-eval.js` — seeds a test portfolio and lets an evaluator play the model against the real tools without an API key (used for prompt/tool evaluation).

## Catalog
`server/catalog/securities.json` holds the plain-English descriptions (official source URL, review date, verification status). Entries were checked against official-source search excerpts on 2026-10-21; re-verify periodically. User edits are stored in the `descriptions` table and take precedence.
