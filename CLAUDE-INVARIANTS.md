# Signal Desk — notes for future development sessions

Read START-HERE.md for the user-facing view. This file covers what you must preserve when changing the code.

## Never break these
- **The user's data is sacred.** `data/signal-desk.sqlite` holds real holdings, entry prices and reports. Never reseed, migrate destructively or overwrite it with example data. Schema changes go in `server/db.js` `MIGRATIONS` as new, additive entries; never edit an applied migration.
- **No trading.** Do not add brokerage order or trading-permission integrations.
- **No silent estimates.** Missing or stale quotes stay missing/stale with a label, and the last valid value is kept. The real workspace never falls back to demo data. Never reconstruct session high/low from scheduled checks.
- **Currencies:** USD and CAD totals are computed separately; combine only with a stored, dated FX rate (`fx_rates`).
- **Instrument identity:** an instrument is `(symbol, exchange)` with a currency. Unconfirmed instruments (`identity_status != 'confirmed'`) are not priced. Ambiguous tickers (catalog `ambiguity`, and SPCX always) get no description until confirmed.
- **Secrets** live only in `.env`, read by `server/config.js`. Everything logged or returned in errors passes through `redact()`. Never send keys to the browser.
- **Local only by default:** `server/index.js` refuses non-loopback binding unless remote access is explicitly enabled with a token. Keep the Host-header, Origin and `X-Signal-Desk` CSRF checks.
- **Untrusted content:** news text is rendered via text nodes (`public/lib/ui.js` `h()`), never `innerHTML`, and passed to the AI analyst fenced in `<untrusted_item>` with a JSON-schema response.
- **Assessments** (`server/assessments.js`) must not derive actions from entry price, must not add on a fall alone or sell on a rise alone, must require confirmed cash for CONDITIONAL_ADD and a complete risk profile for sizing. Action labels come only from rules; the AI analyst only explains.
- **Ask Signal Desk (server/agent/)**: tools are read-only. The only write path is `propose_record_change` → `chat_proposals` (pending) → user Confirm → existing audited functions. `checkUserIntent` requires the quoted request to appear in the user's latest message with an instruction in the quote or in another clause of the user's own words that points back to it, refuses questions, hypothetical framings ("simulate:", "scenario:", "same but … instead"), orders to trade anywhere in the message, future plans, other people's trades and anything inside quoted or attributed text, and requires the change's key values (ticker, quantity, price, amount, type, currency, direction, thesis…) to match that message. `checkAccountAndCurrency` takes the account from the request's sentence (longest match, canonical name), else the one account named anywhere in the message, and asks which currency when the account holds both. `trade_date` must be stated (or today, yesterday, a weekday, N days ago); omitted means today. `positionChange` previews a trade by replaying the ledger with the row as `extra` in `deriveLedger` (never writing to the database), so backdated entries are valued at their date and refused if they break a later entry. `confirmProposal` rebuilds the change and refuses if its `stateKey` (the records it depends on) changed, and is tied to the conversation id. All arithmetic shown to the user comes from `calc.js`/portfolio code, never the model; scenario cash is per account and currency. Unknown fees are never treated as $0: net figures stay null and before-fee fields are returned instead. Every returned record is registered in the turn's `Ledger` (refs R1…) so answers cite sources, including status refs for unavailable data; third-party text is wrapped with `untrusted()` and the user's own notes with `owner_note` (still data, not instructions). The guard and intent check are regression-tested against labelled corpora (`tests/fixtures/guard-corpus.json`, `intent-corpus.json`, run by `tests/guard.test.js`); add a labelled case for every miss or false positive you fix, don't tune a rule without re-running the whole corpus, and measure on sentences you have not tuned on before trusting a change (measured on fresh blind text it had not been tuned on: about 63–64% recall of claims and 93–97% specificity; corpus score is not generalisation). Simulation markers (simulated, paper, backtest, forward test, Strategy Lab, hypothetical account) exempt a trade statement only within its own clause or noun phrase. The guard does not know today's date, so a claim dated today reads as the owner's own recorded trade. `validateAnswer` runs `guardText` from `guard.js` over every answer field (claims that a trade was placed, executed, filled or is in progress, or that a record was changed, judged per sentence by structure — any past/perfect/progressive/emphatic verb with the assistant, the app or no subject acting on the owner's things, passives on owner-scoped nouns, and state claims like "your USD cash is now 0" — not by verb lists; exemptions such as negation, hypotheticals, dates and reported speech count only when they govern the claim's own clause; the loop asks the model once to rephrase before removing them), drops follow-ups that would pass the intent check, relabels `external_fact` points that cite only media reports or archived briefings as `reported_claim`, and adds a `data_gap` note for cited stale market data. Prior turns are sent as plain text only, so each answer re-fetches data. Trade statuses: every ledger item for a trade or order carries `tradeStatus`, set by the tool that read the record: PROPOSED (`propose_record_change`; the proposal's status is its sub-state), SIMULATED (`simulate_trade(s)`; Strategy Lab items of kind simulation) or USER-REPORTED (each transaction row, with origin manual, csv, screenshot or chat_proposal). BROKER-CONFIRMED is reserved and `Ledger.add` refuses it. `validateAnswer` (`tradeClaims` in agent.js) removes trade statements whose stated status no cited record backs (for the short answer, the records are all of this turn's) and always removes broker-confirmed wording; details get `tradeStatuses` from their cited refs only. Regression tests: `tests/agent-trade-status.test.js`. The detector is rule-based and has known misses; re-run the guard corpus before tuning it.
- **Agent loop (`agent.js`)**: `submit_answer` must arrive alone (otherwise it gets an error result and the loop continues; in the last round the bundled calls run first, their refs are not citable, and the answer carries a note, or an issue if a bundled proposal failed); an answer with no tools run is marked partial whenever it states figures or portfolio facts; follow-up chips are checked sentence by sentence against `ACTION_START` and `checkUserIntent`; the automatic stale-data note is suppressed only by a model data_gap that cites the stale ref or names the instrument (ticker or company name) together with a staleness word or quote/price/market data; a text-only reply gets one nudge; large tool results are shortened by `fitResult` (valid JSON, note of what was cut); `budgetCheck` runs before every model call; one turn per conversation at a time (`ctx.chatBusy`); the HTTP layer aborts the turn when the client disconnects. Responses are streamed; content before a server-side `fallback` boundary is dropped (`usableContent`). Spend is priced per model from `usage.iterations` and kept in `data/chat-usage.json`, shared by both workspaces; an unpriced model is refused while a cap is set. Each call reserves an estimate (`reserveSpend`) that `budgetCheck` counts until the call is recorded; a dropped or aborted stream is charged an output estimate from the streamed characters (max_tokens once a thinking block started) so the cap errs high; an unreadable spend file pauses chat (fail closed) and is re-read on every check so deleting it takes effect without a restart. Request options a model rejects (`fallbacks`, `output_config.effort`, strict tools) are turned off one per retry, up to three retries in one call.
- **Tool schemas**: only the tools in `STRICT_TOOLS` are sent with `strict: true`, because the API limits strict schemas per request (20 strict tools, 24 optional and 16 union-typed parameters); `tests/agent.test.js` checks this with `strictSchemaStats`. Strict tools list every property as required (nullable where optional); other tools validate input in their handlers. When adding a tool: register ledger refs for everything it returns (status refs when data is missing), wrap untrusted text, and add it to the no-write test in `tests/agent.test.js`.
- **Ledger maths (`portfolio.js`)**: `deriveLedger(db, { asOf, extra })` replays splits at the start of their effective date; daily P/L converts start-of-session shares to post-split units on a split's effective date, a position's dailyPct uses the same denominator as the totals (start value plus same-session buys), and a position not held during its quote's session has null daily P/L (never the quote's change_pct). `sessionMixNote` flags totals that span sessions.
- **Earnings and FX**: `refreshEarnings` passes listings (symbol, exchange, provider symbol) to providers and records non-US listings a provider cannot check as not covered, never as "checked, no date"; events link to the matched listing. `boc.js` stores every observation of the recent-rates response, and the FX effect in `dailyAttribution` is shown only when the session's rate and the previous Bank of Canada business day's rate are both stored.
